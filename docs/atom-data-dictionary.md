# Atom 业务数据定义说明 v2.0

> **本文档是 Atom 商业业绩指标体系的口径 SSOT**：产品业务定义 + 指标字典 + 后台数据字段定义。
> 战略框架见 [`atom-metrics-framework.md`](atom-metrics-framework.md)；账号档案字段 SSOT = [`ATOM-UserGoalPreference-and-OnBoarding`](https://github.com/Alexis-Lin/ATOM-UserGoalPreference-and-OnBoarding) 仓（下称档案仓）；计费/订单事实 SSOT = 订单系统。
> 版本：v2.0（2026-08-18）｜ 第十轮修订：A3 更名**应用活跃**、A4 更名**训练活跃**（D37）；课程时长类型定名 **workout_length_type**（mini 短练 <5min / short 小课 5–15min 含两端 / long 长课 >15min，原 workout_type 已被『课程类型』占用）；用户分层简化为**轻/常规/重三档**（D38）；仓库新增统计字段定义（schema/）与前后端开发参考（backend/、frontend/）。

## 0. 体系设计原则（结构化审视后确立）

1. **三段式顶层结构**：所有指标归入三个商业问题——**规模**（卖得动吗）→ **参与**（用得住吗）→ **变现**（愿意付费吗）。高管首屏三卡对应命名：**用户规模 / 活跃使用 / 软件订阅**；每卡**先列累计绝对值（盘子），再列关键比率**。
   **展示排序两原则（D27）**：① 激活域内永远**先账号注册（软件层）后设备激活（硬件层）**，ACT01–04 编号依此排定；② Tab 顺序 = 激活 ACT → 活跃 ENG → 训练 TRN → 留存 RET → 会员 SUB → 设备 DEV（训练紧随活跃，同属参与域）。
2. **模块助记编号（v2，D25）**：模块码与看板 Tab 一一对应且在所有卡片/图表显式展示，语义对齐增长 AARRR 框架：
   `ACT` **Activation 获取激活**（账号注册-软件层 + 设备激活-硬件层）/ `ENG` **Engagement 活跃** / `RET` Retention 留存 / `TRN` Training 训练内容 / `SUB` Subscription 订阅会员 / `DEV` Device 设备健康。
   **编号规则**：模块码 + 两位序号、无连字符（`ACT03`）；比率 = 绝对值编号加 **R 后缀**单 token（`ENG08R`）；**P2 二期指标编号自 90 起**（`ACT90`、`SUB90`），一眼识别。
   **模块间关系**：ENG、TRN、RET 同属「参与」域——**ENG 管定性**（账号有没有练，二值 UV），**TRN 管定量**（练了多少/多深，多为 PV），**RET 是参与的时间维展开**。阅读顺序：ENG 有没有 → RET 还在不在 → TRN 练得怎样。
   ⚠ **勿混**：活跃层级 **A1/A2/A3**（A = Active，属 ENG 模块的内生维度）与模块码 **ACT**（Activation）无关。
3. **阶段纪律**：每个指标标注 **P1**（一期，仅依赖后台服务器数据）或 **P2**（二期，依赖 Shopify/手工报表/多币种金额等外部接口）。**P2 指标不上一期看板**——数据缺口不冒充指标。
4. **比率优先**：绝对量用于定规模，判断一律用比率（转化率、渗透率、留存率、Quick Ratio）；跨 cohort、跨地区才可比。
5. **无金额条件下的价值代理**：一期不做收入金额（多地区价格/汇率口径未统一）——用 **付费 Pro 数 × 会员在订时长（tenure）× Pro 占比** 作为价值代理组合；金额指标随 P2 计费接口统一后接入。
6. **克制**：不做复合"健康分"（伪精确）、不做双轴图、权益用量类指标降级 P2（业务方判断暂不重要）。

## Part A · 产品业务定义

### A-1. 产品与账号基础

| 术语 | 定义 | 备注 |
|---|---|---|
| **ATOM 设备** | 便携 AI 健身摄像头（`identity.devices[].device_type = atom`），配合手机 App 使用 | 档案仓 §10.3 |
| **账号** | `user_id`（ULID，全局主键）。中国大陆与国际是两套隔离账号体系：`account_edition ∈ cn / intl` 为数据驻留分区键 | 档案仓 §10.1 铁律④ |
| **产品线 `product_line`** | 一级维度，直接取 `account_edition`：CN / INTL；INTL 下钻 `country_code` | |
| **App 注册** | 账号创建成功（email 必有） | cn=手机号、intl=邮箱主路径 |
| **设备配对激活** | 一台 ATOM 首次进入 `devices[].state = bound`。**一台设备终身只计一次** | none → purchased → bound ⇄ unbound |
| **已绑定激活账号** | 历史上完成过 ≥1 台 ATOM 首绑的账号 | 活跃/留存/渗透率分母 |
| **业务日** | America/Los_Angeles（PT）自然日，全球统一，夏令时随美国 | 中国版分析配北京时间辅助视图 |

### A-2. 四层活跃（A1 ⊇ A2 ⊇ A3 ⊇ A4，账号主键；A = Active 层级，属 ENG 模块，勿与模块码 ACT 混淆；D32 会议升级）

| 层 | 名称 | 当日判定（PT 日界，按 `user_id` 去重） | 定稿 |
|---|---|---|---|
| **A1** | 开机活跃 | 名下任一 ATOM 有开机/唤醒/物理交互事件（可离线产生；含相册等本地浏览） | 近 7 日回填，第 8 天定稿 |
| **A2** | 联网活跃 | 名下任一 ATOM 与云端有有效心跳或数据同步 | T+1 |
| **A3** | 应用活跃 | 当日有任一 **App 会话**（任意 app_category：桌面/语音/运动均计） | T+1；App 会话需联网上报 → A3 ⊆ A2 |
| **A4** | 训练活跃 | 完成 ≥1 次**有效训练**（仅 PHYSICAL 类会话） | T+1；**A4 ⊆ A3** |

**设计说明（会议共识的嵌套化）**：会上提的"桌面功能活跃"若单设一层会破坏嵌套（只练不挂桌面的人无法归层）。因此 A3 定义为「任一 App 会话」保持严格嵌套，**桌面陪伴场景用两个读数呈现**：① 差值 **A3 − A4 = 纯桌面陪伴账号**（用了应用但没训练）；② ENG16 分 App 类活跃里的 DESK 曲线。两个视角都能回答"桌搭场景有多少人在用"。

### A-3. 有效训练与活跃质量

| 术语 | 定义 |
|---|---|
| **有效训练** | 单次训练会话中，**完成 ≥1 个完整组，或训练时长 ≥1 分钟** |
| **完整组** | 按课程/动作的完整性定义**完成即计**，组内次数不作限制 |
| **训练时长** | 后端已有上课时长统计（D21/R14 ✅）；有效运动时长（扣暂停）作为增强项跟进 |
| **课程时长类型** | **由课程属性打标（D33），字段名 `workout_length_type`（D37：原拟 workout_type，已被『课程类型』占用）**：内容侧给每节课标注三档——**`mini` 短练（<5 分钟）/ `short` 小课（5～15 分钟，含两端）/ `long` 长课（>15 分钟）**，前端可暂不展示、统计先用。**时长课型 = 用户意图维度**；与**实际维度**（实际训练时长、完成度）正交，两套都看——"总点长课但上不完"与"只上短练但完成率高"是不同的经营故事 |
| **完成/完课** | 完成 = 完成度 ≥ 阈值（**阈值待定 R20**，候选 60/70/80%，暂按 70% 占位）；<10% 视为即点即退（drop） |
| **set 归一化** | 组（set）≈ 1 分钟/10 次上下——作为跨 App、跨课型的统一度量单位（周人均组数可跨口径比较） |
| **深度训练** | 单次 ≥2 完整组 且 ≥5 分钟 |
| **负荷 load** | 用户自填（无阻力传感器）。基于 load 的指标必须同报**自填负荷覆盖率** |

**A-3b App 三分类（D31 · 内生维度 `app_category`）**

设备上有多个 App（Workout、桌面跳绳、体态监测「抬头番茄」、One Set 计组等），且会持续增加。**按交互形态归入三类**，新 App 上线先归类再上报：

| 类 | code | 定义 | 示例 | 计入哪层活跃 |
|---|---|---|---|---|
| **身体运动类** | `PHYSICAL` | 需要身体真实运动的训练 | Workout、桌面跳绳、One Set | 计入 A3 应用活跃；**唯一计入 A4 训练活跃 / 有效训练**的类 |
| **桌面参与类** | `DESK` | 被动坐在桌前参与 | 体态监测「抬头番茄」 | 计入 A1–A3；**不计 A4**——挂机一下午不能算"练了" |
| **语音交互与把玩类** | `AMBIENT` | 纯语音交互、桌面查看/把玩 | 语音助手、表盘查看 | 计入 A1–A3；不计 A4 |

- **口径红线**：有效训练判定（≥1 完整组或 ≥1 分钟）**仅对 PHYSICAL 类会话生效**——否则运动指标被桌面挂机污染。One Set 按组计数天然适配"完整组"判据；跳绳按跳绳段计组。
- DESK 类另设**参与时长**口径（分钟 PV，判定阈值待 R19），与训练时长分开、不混算。
- 分 App 活跃 = ENG16（各类 DAU/WAU 账号数，**类间可重叠**——一个账号一天可能又练又挂体态监测；不是 MECE 分层，是使用画像）。

### A-4. 会员体系（第四轮修订）

```
FREE ──首次绑定 ATOM──▶ PLUS（账号终身免费，解绑设备不回落 · D18）
                          │
                          ├─购买套装 →激活→ 用户自行兑换──▶ PRO_GIFT（赠送 1–12 个月）
                          │                                    │到期
                          ├────────自费开通──▶ PRO_PAID ◀──转付费┘
                          └──────────────────（到期未续 → 回落 PLUS）
```

| 状态 | 定义 |
|---|---|
| `FREE` | App 注册，从未绑定 ATOM |
| `PLUS` | 历史上完成过首绑，**会员随账号终身保留**（跟人不跟机，D18） |
| `PRO_GIFT` | Pro 权益有效，来源 = 套装赠送（**兑换制**：购买后需用户主动兑换，D19），gift_months ∈ {1…12} |
| `PRO_PAID` | Pro 权益有效，来源 = 自费订阅 |

**要点：**
- Plus 不是转化指标（≈ 已绑定激活账号数）；会员生意的看点在 Pro。**NSM-2 = 活跃付费 Pro 数**（不含赠送期）。
- **赠送是兑换制 → 会员漏斗多一个泄漏点**：`购买套装 → 激活 → 兑换赠送 → 赠送到期 → 转付费 → 续费`。**兑换率（SUB05）与赠转付转化率（SUB06）并列为漏斗关键指标**——没兑换的用户连体验 Pro 的机会都没有，是最便宜的挽回。
- 一期只看**会员等级与时长**（tenure），不看金额（多地区价格/汇率，P2）。
- 权益配额（D20 记录）：AI 课 Plus 20 小时/月、Pro 200 小时或不限；视频存储 Plus 5G、Pro 100G。**用量指标列为 P2**（业务方判断暂不重要）。
- cancel_pending（已取消待到期）仍计 PRO_PAID，单独出占比作流失先行指标。

### A-5. Cohort 与留存

同 v1.0：起点 = 首次绑定激活日；周（主）+ 月 cohort，自 2026-04；Wn/Mn 区间留存按 A1/A2/A3 各一套；D1/D7/D30 精确日留存；Churned = 28 天无 A1；Quick Ratio = (New+Resurrected)/Churned。

### A-6. 数据定稿与跨区合并

同 v1.0：A1 层 7 天回填窗口（超窗丢弃留档监控）；CN/INTL 用户级数据隔离，仅指标级合并（`global_metrics_daily`）；**退货与售出数据一期不接**（D22）——REG 模块 P2 组依赖 Shopify + 手工报表，二期接入。

### A-7. 计数口径与单位规范（PV / UV）

> 每个指标必须能回答"计人还是计次"。看板每张卡/图的副标题注明单位与口径。

- **UV（去重口径）**：按主键去重后的数量——账号类按 `user_id`，设备类按 `device_id`。**凡未特别标注的指标默认 UV**。
- **PV（次数口径）**：事件累计次数，不去重（课次、组数、绑定尝试、补传事件等）。
- 比率类指标必须写明分子分母各自的口径（如 完成率 = 完成次 ÷ 开始次，PV/PV）。

| 指标族 | 单位 | 口径 |
|---|---|---|
| ACT03/02 激活 | 台 | **设备 UV**（终身一次） |
| ACT01/04 注册 / 绑定账号 | 账号 | 用户 UV |
| ACT05 注册→绑定转化 | % | 账号 UV / 账号 UV |
| ENG01 活跃矩阵（4 层 × 3 窗）、分层、静默 | 账号 | 用户 UV |
| **有效训练人数（漏斗段）** | 账号 | **计人不计次**（激活后完成过 ≥1 次有效训练的账号 UV） |
| ENG13 周均训练次数 | 次/账号/周 | PV ÷ UV |
| TRN01/02 Starts / Completions、组数 | 次 / 组 | **PV 不去重** |
| TRN03 完成率 / TRN04 完成度 | % | 课次 PV 口径 |
| TRN06 TTFW / ACT91 激活时延 | 天 | 中位数 + P90 |
| 时长类 | 分钟 | Σ时长（PV）；人均 = ÷ 账号 UV |
| RET 留存率全部 | % | 账号 UV / cohort 账号 UV |
| SUB 全部 | 账号 / % / 月 | 用户 UV；tenure 单位=月 |
| DEV01/02 | 台 / % | 设备 UV |
| DEV05/06 补传延迟/丢弃 | 事件 | PV |

### A-8. 数据分层（埋点 → 派生）与维度分类

> 用途：校验与溯源。任何数字可疑时，沿四层 lineage 从上往下拆；任何新指标入库前，先在本节找到它的层与维度归属。

**A-8.1 四层 lineage**

| 层 | 性质 | 内容 | 校验方式 |
|---|---|---|---|
| **L0 原始事件** | **需埋点/接口**；append-only 不可改写 | 见 A-8.2 清单 | 上报量监控（DEV05/06）、覆盖率指标（TRN16 等） |
| **L1 日快照** | 由 L0 按日展开/判定，无新信息只有整理 | `agg_user_daily`（a1/a2/a3 flag、有效训练判定）、`agg_membership_daily`（状态机按生效区间展开）、`bridge_user_device` | 抽样账号对 L0 事件重放比对 |
| **L2 计数指标** | L1 之上的 count / sum / distinct | 全部绝对值类：ACT03…04、ENG 矩阵、TRN 次数/组数/时长、SUB 各状态人数、DEV 台数 | 按交叉维度切分后加总 = 总量（可加性检验） |
| **L3 比率/复合** | **两个 L2 指标的商或组合，无独立数据源** | 全部率（R 后缀、转化、留存、渗透、完成）、Quick Ratio、tenure、时长课型 Mix、人均类 | 分子分母必须都是表内已编号指标，可手工重算复核 |

**A-8.2 L0 原始事件清单（埋点状态）**

| 事件 | 来源 | 埋点状态 | 喂养指标 |
|---|---|---|---|
| `app_registration` | App 后端 | ✅ 已有 | ACT01/05 |
| `device_binding_event`(bind/unbind) | App/后端 | ⚠ **需新增**——档案仓 devices[] 只存当前态，分析需要历史事件流 | ACT03/02/04/07、bridge、PLUS 判定 |
| `onboarding_step` / `wifi_setup` | App/固件 | ⚠ 需确认现状 | DEV04（配网质量，绑定流程问题归此处） |
| `device_power_on` | 固件（离线本地缓存，7 天补传） | ✅ 已有（D5/D8） | A1 → ENG 全系、RET |
| `device_heartbeat` | 固件 | ✅ 已有 | A2、DEV01 |
| `session_start/end`（全 App 统一，带 **app_id → app_category**） | App/算法侧 | ⚠ 需扩展——现有仅 Workout 会话；跳绳/One Set/抬头番茄等需统一 session 事件模型并携带 app_id（会议确认：除相册等本地浏览外，App 均需联网使用） | A3 应用活跃/A4 训练活跃、ENG16/17/18、TRN 全系 |

| `quota_usage_daily` | 业务后端 | P2 | SUB90…93 |
| `ota_event` | 固件 | ⚠ 需确认 | DEV02/03 |
| 售出/退货 | Shopify + 销售手工 | **P2 不接** | ACT90…93、DEV90 |

**A-8.3 维度分类（三类，别混）**

| 类 | 定义 | 清单 | 校验要点 |
|---|---|---|---|
| **交叉维度**（任何指标都可切） | 独立于指标存在的切片轴 | 时间（日 / ISO 周 / 月，PT 日界）、product_line（CN/INTL → 国家）、激活 cohort（周/月）、渠道、SKU、固件版本、会员状态 | **可加性**：任一 L2 指标按交叉维度切分后加总 = 总量；率类切分后不可直接加总（需重算） |
| **内生维度**（只属于某族指标） | 指标定义内部的分解轴 | 活跃层级 A1/A2/A3、**App 分类 PHYSICAL/DESK/AMBIENT**（ENG16 类间可重叠，非 MECE）、课程时长类型 mini/short/long（D37）、赠送月数 1–12、用户分层 轻/常规/重（D38 三档）、计费周期、权益来源 gift/paid | **MECE**：各档互斥且完备，分档加总 = 全量（如 Plus+ProGift+ProPaid+Free = 全部账号） |
| **比例关系**（不是维度，是 L3 派生） | 两个已编号指标的商 | 活跃率（R 后缀）、ACT05、ENG10/11、RET 留存率、SUB03…06/08/10、TRN03 | 分子的口径域 ⊆ 分母；分子分母编号在字典可查；**换分母必须换指标名**（防止同名不同率） |

## Part B · 指标字典

> 列：编号 / 指标 / 口径 / 期。默认维度：`product_line` + 日期（PT）；★ = 高管首屏。P1 = 一期（后台数据即可）；P2 = 二期（外部接口）。

### ACT · Activation 获取激活（账号注册 + 设备激活）

| # | 指标 | 口径 | 期 |
|---|---|---|---|
| ACT01 ★ | App 注册账号数（软件层） | 累计/新增，分 edition | P1 |

## Part C · 后台数据字段定义

### C1. 账号档案字段（引用档案仓）

同 v1.0（user_id / account_edition / email / personal / devices[] / acquisition / membership_tier / goals[].code / weekly_frequency / log.bodypark / log.analytics）。会员补充：**membership 权益随账号（D18）**——档案仓 `membership_tier` 语义不变，判定与设备解绑无关。

### C2. 埋点与业务事件

同 v1.0（公共字段 event_id + 双时间戳 + account_edition），修订两处：

- `workout_session_end`：**duration 后端已有统计（D21）**，直接消费；active_duration 作为增强字段跟进。
- `membership_event` 增加事件：**`gift_redeem`（用户兑换套装赠送）**——兑换率 SUB05 的来源；`entitlement_source(bundled_gift/self_paid)` 与 `gift_months` 仍为必需扩展。
- `dim_content` 增加 **`workout_length_type`**（`mini` 短练 <5min / `short` 小课 5–15min 含两端 / `long` 长课 >15min）——内容侧逐课标注；原拟名 workout_type 因已被『课程类型』字段占用而改名（D37）。`session_start/end` 冗余快照该字段，统计以 dim_content 为准。
- 一期**不接** `fct_sales_manual`（售出/退货）——REG P2 组与 DEV90 随 Shopify + 手工报表接口二期启用。

> **机器可读定义（本仓库，v2.0 新增）**：埋点事件信封与 payload 见 `schema/events.schema.json`；指标注册表见 `schema/metrics.json`（看板 ⓘ 提示与口径 Tab 的单一数据源）。

### C3. 数仓模型

同 v1.0 的每区一套 + `global_metrics_daily` 指标级合并，变更：

```
agg_user_daily        字段名更新：a1/a2/a3 flag（原 l1/l2/l3）
agg_membership_daily  增加：redeemed_at?（兑换时间）、tenure_months（在订月数，滚动累计）
dim_sku_gift_map      SKU → gift_months；由后台套餐定义表同步（价格字段暂不消费）
dim_app               app_id → app_category(PHYSICAL/DESK/AMBIENT)、app_name —— 新 App 上线先归类（D31）
dim_content           content_id → workout_length_type(mini/short/long)、planned_duration_sec、set_count（D37）
agg_user_daily        增加：mini/short/long_workout_cnt（按时长课型拆分的有效训练次数）
（移除一期范围：fct_sales_manual）
```

> **建表与推导 SQL 参考（本仓库，v2.0 新增）**：数仓 DDL 见 `backend/ddl.sql`；指标推导 SQL（基座构建、ENG01 矩阵、ENG08/08R、ACT05、ENG14 三档、RET01/RET06、TRN08/19、GLOBAL 汇总）见 `backend/metrics.sql`；前端接口契约与原型接数指引见 `frontend/api-contract.ts`、`frontend/README.md`。

### C4. 数据质量与治理

同 v1.0；增加：P1/P2 标签入指标字典元数据，看板不渲染 P2 占位。
